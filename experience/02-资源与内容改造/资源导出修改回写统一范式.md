# 资源导出修改回写统一范式

更新时间：2026-03-11  
来源：多项目实战沉淀（案例见 `experience/90-项目案例归档/`）

## 使用说明（示例与通用边界）
- 文中 `Main_Level_N`、`Story_N`、`Others` 属于目录组织示例。
- 文中 `sourceImages`、`manifest`、`atlas` 为通用概念示例，可按项目实际命名映射。
- 已有可靠Sprite映射时采用“分图编辑 -> 映射管理 -> 合图重建 -> 回写校验”；仅有整纹理工具时采用“整纹理编辑 -> manifest尺寸/身份校验 -> 原路径回写”。不能把推荐目标当成现有实现。

## 目标
- 导出后按工具实际能力编辑分图、整纹理或可读配置；必须标记导出层级。
- 回写时由脚本负责还原到游戏真实资源格式。
- 避免人工改合图导致映射错位、CRC 错误、游戏不生效。

## 导出标准（sourceImages）
- 根层级允许：
  - `Main_Level_N/`（主线关卡分图）
  - `Story_N/`（故事模式分图）
  - `Others/`（其他 Level 资源分图）
  - 根目录平铺分图（非 Level 贴图）
- 分图链路中Atlas作为中间产物；本库Cocos整纹理链路的`textures/`本身就是编辑输入，须保留，不能照搬分图目录约束。

## 映射标准
- 维护独立映射文件（例如 manifest/json）：
  - 分图文件名 -> 合图名 -> 裁切位置/尺寸
  - 分图文件名 -> 目标包/目标资源路径
  - 关卡与资源包关系（由配置表推导，不靠文件名猜测）

## 回写标准
1. 读取映射，先检查所编辑分图或整纹理尺寸与原始记录一致。
2. 需要合并的资源先重建合图（临时产物，不落 `sourceImages`）。
3. 用重建后的合图回写目标包/目标文件。
4. 写回后做完整性校验（哈希/CRC/可加载性）。
5. 运行游戏验证修改是否在目标场景生效。

## 典型故障与处理
- 修改后不生效：
  - 先查是否回写到了真实被引用的合图。
  - 再查 UnityCache/浏览器缓存。
- 进入下一关报 bundle CRC/404：
  - 说明写回后包体内容与索引/manifest 不一致，需重建并校验全链路。
- 文件名与内容错位：
  - 说明映射错配，禁止按文件名猜路径，必须按配置表/映射表回写。

## 图片资源名错位（本次高频卡点）专项规范
- 现象（以 `drgm_ljpx2_lt` 为例）：
  - 分图文件名看似正确（如 `...__0003_159.png`），但图片内容对应另一个角色。
  - 进而导致“按分类分目录”看起来错乱（例如 `ct198_蓝发` 目录里出现老人/戴帽子）。
- 真实根因：
  - 不能假设 `SpriteAtlas.m_PackedSpriteNamesToIndex` 与 `m_RenderDataMap` 是同序一一对应。
  - 实际存在“名称顺序”和“渲染数据顺序”不一致的情况，按索引硬配会错位。
  - 还存在“像素在当前 Atlas 包，Sprite 元数据在共享包”的跨包结构；只看单包会丢失正确映射。
- 正确做法：
  - 用 `Sprite.m_RenderDataKey` 建立映射，不用“同索引猜测”。
  - 建立双向表：`atlasTag + spriteName -> renderKey`，`atlasTag + renderKey -> spriteName`。
  - 再用 `renderKey -> renderData(textureRect)` 裁切，最终得到正确 `spriteName -> png`。
  - 对外统一稳定主键：`imageKey = bundleHash#atlasIndex`，不要只靠文件名做身份标识。
- 强制门禁：
  - 抽检至少 1 个已知关卡（例如 NH1）做“游戏内布局 vs 导出文件”人工对照。
  - 全量校验必须按 `(itemId, groupId)` 计数比对，不能把 `itemId` 当全局唯一键。
  - 通过后再允许批量按分类重组与回写。

## 最小门禁
- 关键分图修改在游戏内可见。
- 关卡切换无新增 CRC mismatch。
- 回写日志可追溯到“分图 -> 合图 -> 目标资源”链路。

## Unity iOS 单包提取补充

重组日期：2026-08-11  
新增来源：Light Up Sort iOS Unity IL2CPP 资源提取案例

- iOS Unity 单包的资源主体可直接位于 `<App>.app/Data/data.unity3d`，应先做对象类型与 SerializedFile 清点，再决定是否存在 Addressables 或外部分包。
- `PathID` 只在单个 SerializedFile 内稳定；跨文件清单统一使用 `(assetsFile, pathId)`，不能把 PathID 当作全包唯一键。
- IL2CPP 业务 MonoBehaviour 缺少 TypeTree 时，仍可读取 Unity 通用对象头。对于只包含数组/PPtr 的索引对象，可从原始序列化数据恢复引用链，但必须校验数组长度、目标对象类型和解析唯一性。
- Sprite 导出应追踪 `Sprite.m_RD.texture`：裁切后的 Sprite 进入可编辑美术目录，底层合图留在日志或中间层；没有 Sprite 引用的独立纹理再作为 Texture2D 输出。
- `0 × 0` 的 `Font Texture` 常是占位对象，应在清单中标为不可导出，而不是当作资源损坏或中断全流程。
- Mesh、Material、Texture 应分别保留稳定映射；裸 Mesh 可先导 OBJ，若要还原完整关卡模型，还需继续解析 Transform、Renderer 和材质实例链。


## 2026-10-09 通用补充：资源身份与独立校验

当格式包含多个名称表、索引表、图集或跨包元数据时，不假定数组同序，也不把文件名当唯一身份。优先用格式提供的稳定对象键建立双向映射；跨文件键应包含文件/包作用域。保留“原始对象 -> 导出文件 -> 重建资源 -> 目标引用”的映射与哈希。

批量处理前，用已知样本与独立的原程序/原工程画面对照。抽样校验通过后再批量改名、分类或回写；完整性校验还要覆盖下一关/下一个资源包和真实运行时加载。
