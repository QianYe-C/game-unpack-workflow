# Pico Rally 原生运动逆向与 PixiJS H5 移植阶段复盘

重组日期：2026-09-08。

## 目标与状态

遵循 cocosgame 六目录流程，将用户提供的 Pico Rally 1.4 IPA 转为 PixiJS H5，优先还原车辆运动。已交付可玩工程与静态包；主要控制公式与换道决策已经原 ARM64 指令验证，Apple SpriteKit 刚体积分探针通过，145 赛道全圈数回归通过。整游严格 1:1 尚未验收，不将局部等价或相似截图声称为整游完全一致。

项目工作区：`myprojects/picorally/`。原版实际为 Objective-C + SpriteKit，非 PICO-8 / Cocos。

## 阻塞与根因

1. IPA 没有 Web 源码，普通字符串检索无法解释漂移。原始 CgBI PNG 也不能直接交给浏览器。
2. otool 的 ObjC 消息注释在复用 selector 寄存器时不可靠，不能按注释直接翻译。
3. SpriteKit offscreen 探针用时间 0 起步只推进首帧，容易误判积分机制。
4. Planck 车头角度无限累计，SpriteKit 返回归一化角度；仅做首圈检查会漏掉后续圈数差异。
5. 坡道碰撞层若取起始 z，会让车在上坡后才启用护栏，可能从外侧卡住。原版取 max(zStart,zEnd)。

## 动作

- 原包入库 input，解出 plist 和 SQLite / NSKeyedArchive。导出 145 赛道、48 车型配置和 637 纹理，保留全部来源映射。

## 2026-09-08：Nakama、统一回放和目录迁移

用户明确指定新维护位置 `/Users/jiaojian/Documents/picorally/client`、`server`，覆盖工作流默认 webprojects 路径；原 IPA、分析与原有工程保留归档。已终止旧 5178 进程，并以新 client 为 cwd 启动 Vite，核对监听进程与实际 HTTP 入口。

车辆、道路和可移动装饰物现在在纯逻辑初始化器创建。Nakama 和浏览器直接使用同一份控制、赛道、碰撞体及车型数据。房间 30 Hz，每次两步 60 Hz 控制、每步两次 120 Hz 物理；没有为了联网改变原车手感或 AI 惩罚。服务器约 15 Hz 发带帧号的确认状态，自车短程预测纠正，远端按服务器帧时间插值，而非按抖动的到包间隔改变速度。

本地 Docker 原先没有 Nakama，新增独立 picorally Compose 项目、PostgreSQL 卷及 Nakama 3.40.0。API 7350 支持 LAN，控制台仅本机 7351。Goja 默认 16 个预热 VM 改为 1 个，避免本地无谓内存占用。

实际双客户端测试发现直接把循环引用的 Planck World 放入 Nakama handler 返回 state 会触发 Go `pointerizeSlices` 无限递归、进程重启。检查 v3.40.0 上游 match core 源码确认每场独占一个 VM 后，改为房间 VM 内闭包保存 World，返回 state 只放普通 tick/phase。不能把此做法泛化成跨 RPC 共享全局变量；升级 Nakama 必须检查 VM 生命周期并重测多房间。

历史回放与影子统一为 HistoryRecord，保存带帧号的全车、拖车、可移动物体、车辆控制状态及版本/赛道/发车槽位元数据。联机只记录服务器确认状态，预测轨迹不入库。回放可暂停、0.5/1/2/4 倍速、拖进度；IndexedDB 最近 10 把按时间淘汰。最快兼容完赛记录放同数据库的独立 best store，不受历史淘汰影响；影子只是该记录的一辆车轨迹投影，不新增物理车体，不是模式。不同发车阵容和 P1/P2 起跑位分别比较。

验证证据位于新项目 logs：15 项单元测试、145 赛道完赛、双浏览器同帧确认状态/完赛结果一致、含约 140 ms 基础 RTT 与有序抖动的预测误差、断线判负；完整回放的暂停/拖动/倍速、12 把真实油门测试后的 10 把保留、历史淘汰后最快影子保留、开关功能；原面对面双人、显示插值和粒子回归保留。

边界：当前是权威状态同步，未宣称严格确定性锁步。客户端只恢复物理可见状态和控制变量，没有完整 Planck 接触缓存回滚；本地两局 Cork 的小误差不代表所有赛道/弱网都无纠正。录像、影子存在本机浏览器，尚无账号云同步、全球最强录像榜、断线重连或正式公网部署。回放复现逻辑状态，视觉粒子重新生成，并非像素级视频。

## 2026-09-08：镜头基础距离核对

用户反馈镜头太远。原始 UIView bounds 初始化 GameScene，再将场景尺寸乘手机 2.85 / iPad 1.5；因此 Pixi 缩放应取倒数，而非继续按设计宽度缩小。核对 handleCamera 的分支发现原生动态缩放属于多人共享镜头，单人分支只跟随相机目标；旧 H5 的随速度再缩小最多 20% 没有这一分支依据，已删除。

新 client 单屏 / 联机 / 回放共用原版基础倍率，同屏双人沿用整屏设备类别，再对不足 320 CSS px 的浅视口保留最小视野。600 CSS px 的设备类别断点和浅视口策略是 H5 适配，跟随目标与平滑仍未逐帧还原。八组浏览器画幅记录在新项目 `logs/camera-before.json`、`camera-after.json`；390 × 844 手机同输入行驶缩放从 0.240279 改到 0.350877，车辆尺寸增加约 46%。DPR 2/3 一致，静止 / 加速倍率一致，分屏朝向和地图往返正常；构建及既有视觉回归通过。详细地址见新 `client/CAMERA.md`。

用户随后提供 750 × 1334 手机截图，补充发现初轮仅取 1 / 2.85 仍遗漏 320 点兼容画面到实际屏幕的放大。原包手机 LaunchImage 只有 320 宽；源 r2.png 两侧护栏间距 224 世界点，截图测得约 184 像素，与 224 × 750 / (320 × 2.85) = 184.21 一致。手机现按视口短边 / (320 × 2.85) 缩放，375 CSS px 比初轮再放大 17.1875%。九组画幅与修改前后同输入物理位置检查通过；原版逐帧跟随位置仍未凭单张图冒称一致。新证据为 logs/camera-reference-* 与 client/CAMERA.md。


## 2026-09-08：每周挑战、手机 UGC 工坊与路线反馈

新维护 client 主菜单补独立每周挑战（原 30 条、北京时间周一轮换、本地成绩）和 UGC 工坊。钢笔直线/贝塞尔曲线采样，闭合校验后编译为共享 RoadTile，使用已有真实车辆控制与碰撞初始化器试玩。纯几何推荐线采用有界曲率平滑与前后向速度限制，并非原版 generateOptimalLanes 的逐项移植或全局最快圈时。原版赛前按路块几何生成三车道，再按后续转角选择车道和速度；原 ARM64 函数、离线导出数据与 UGC 算法须明确区分。
