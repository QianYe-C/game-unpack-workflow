# Unity 运行时组装与收集动画验证

2026-09-08，从 Going Balls 3.40 阶段提炼。参数属于该案例，不应套用于其他游戏。

## 可复用流程

1. 固定版本、架构和输入哈希。分离资源一致性与原生代码地址一致性；相同 assets 不代表 ARMv7/ARM64 地址可复用。
2. 记录 prefab 保存态，再恢复 Init、OnLevelEnablePhysics、Reset 等方法产生的运行态。检查动态加载的平台、门、收集物以及 disabled collider。
3. 将渲染合批与逻辑/碰撞 ID 解耦。父级会动画的后代不能静态合批；同 prefab 多实例要加独立作用域，不能直接复用 PathID 为全局键。
4. 从触发事件追到当前游戏状态处理函数，再追动画控制器。资源包内同名/近名旧类必须有实际调用链才能作为实现依据。
5. 分清收集触发、逻辑记账、模型飞行、视觉隐藏和 HUD 更新五个时点。测试连续触发、暂停、重置、切关及重复领奖。
6. 屏幕目标的 3D 飞行应记录起点所属空间、父级改变是否保留世界变换、相机参数、射线距离、缩放和旋转曲线。纯 CSS 图标平移通常不能直接等同源 3D 模型过渡。
7. 验证 Worker 时使用和主线程相同的固定步进代码，触摸增量不可因批量子步被重复消费；复活时必须废弃旧的跌落状态与在途消息。
8. 颜色差异先验证源色彩空间和实际 shader 程序，再看材质/灯光。克隆自定义材质时确认 onBeforeCompile 与缓存键是否保留。
9. 把首次 shader 编译与稳定帧率分开测量。共享几何/材质、实例粒子池及加载期预编译需同时检验资源释放。
10. 对比内存先统一口径：原生 PSS、浏览器 JS heap、GPU 资源估计分别记录；不能混为一个内存倍数。

## 验收证据

源文件/方法体与常量 → 原版操作录像 → 移植帧序列/状态 → 自动回归 → 同设备性能。每层证据只证明自身范围；源码推导不替代原版运行，浏览器通过不替代小游戏真机。

## 全关卡扩展时的补充规则

- 先找实际调用的重载和模式入口。存在随机算法，不代表主线使用随机；代码内置组合表可在用户授权的本地运行实例中只读提取，保留版本和来源哈希。
- 同一个 prefab 的 setup1…5 可能是互斥方案。原版会销毁未选中的对象；仅按序列化 active 导入会生成多余障碍和 draw call。机制代表关号应在选关、方案筛选之后计算。
- Unity builtin mesh 引用不必然是缺资源。把 unity default resources 显式纳入导出环境，避免依赖惰性解析后索引不全。
- 保存原始资产清单和实际运行态清单，两者用途不同。普通/bonus/循环与模式表都需要追溯，运行时传送门/生成器等附加物单独登记。
- 用户在验证途中购买权益或改变库存后，旧备份不能整档恢复。恢复进度应以当前完整存档为基底，仅复制允许的进度字段，比较全部其他字段不变；失败回滚使用本次操作前的新备份。
- 目录/配置已下载与关卡已经初始化是不同阶段。对外 ready 必须在实际关卡创建后才成立，避免自动化或玩家操作读到未就绪对象。
