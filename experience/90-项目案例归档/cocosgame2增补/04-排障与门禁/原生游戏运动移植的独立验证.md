# 原生游戏运动移植的独立验证

重组日期：2026-09-08。来源：Pico Rally 原生 SpriteKit → PixiJS 案例；以下为跨项目方法。

## 将控制器与引擎分开验证

先确定输入到力/力矩/速度修正的映射，再验证刚体积分与接触。仅凭相似跑圈视频或手调速度，无法证明原逻辑已还原。控制器没有可读源码时，可执行原机器码，只在容器和引擎接口处做最小 stub，保留原浮点舍入和数学函数。

测试样本须来自原实现，不能让被测移植代码同时生成期望值。记录入口地址、输入状态、替代的边界、输出、环境和容差。轨迹几何或 AI 速度如果由原程序生成，优先执行原生成器。

## 浮点与角度边界

ARM64 的 s 寄存器表示 float32；移植到 JavaScript 时局部舍入会改变阈值附近的分支。先保持运算顺序，再只在有证据的边界使用 fround。

引擎返回的角度范围可能与新引擎不同。单圈很像、第二圈变差，首先检查是否存在无限累计角度与单次 ±2π 归一化的不匹配。测试应包含多圈、交叉路、坡道与路面变化。

## 原生物理探针

建立独立的最小刚体，只施加已知力与力矩，逐步记录位置、速度、角度、角速度。检查单位换算、惯量、子步、施力顺序、阻尼形式和 force 清理时机，不要从参数同名推断实现相同。

SpriteKit 的 SKRenderer 探针应使用有效的绝对单调时间戳基准；时间从 0 起步可能只推进首帧。需要实际渲染与事件循环，确认每帧都在推进后，才使用输出建立回归。当前系统探针不能证明历史系统碰撞求解器完全一致。

## 碰撞分类也属于玩法

还原 category、collision mask、contact mask，以及进入路段时的切层时机。接触通知不代表刚体碰撞。不要把原来用于减速反馈的传感器全部改成实墙。

坡道层级要追踪源 getter 的实际值，而不是按视觉直觉取起点、终点或平均值。动态创建边界的游戏还要限制参与碰撞的路段，防止远处交叉路错误阻挡。

## 验收结论分层

分别报告原资源提取、控制函数、引擎积分、完整比赛与逐像素视觉的证据。批量赛道能跑完是可运行性检查，不是原机同输入轨迹等价证明。无法验证的模块要列具体范围，不以“基本一致”覆盖未测部分。

## 必须检查构建产物

PixiJS 异步加载 WebGL 渲染器时，Rollup 可能把共享导出放在入口 chunk。入口若使用顶层 await 等待 Application.init()，动态渲染器又依赖入口，就会出现循环等待：开发模式正常，构建模式首屏一直 loading，也可能没有 console error。将异步启动放进普通 bootstrap() 函数，让入口模块先完成求值；然后在静态 HTTP 服务下用构建包重跑操作流程。仅 tsc / vite build 成功不足以验收。


## 2026-09-08 补充：权威联机与回放

- 服务器/客户端复用纯场景初始化与物理核心；纹理加载不得决定碰撞物是否存在。
- 分别测房间 tick、控制步、物理子步与渲染率；降低消息频率不等于改写原来按帧累加的车辆控制常量。
- 确认状态相同与预测画面平滑是两项验收：前者比较同服务器帧的完整快照，后者比较先前预测和后到确认的同帧位置，并检查逐渲染帧位移。
- 弱网测试必须在 WebSocket 收发层施加有序延迟/抖动，仅设置 HTTP 请求延迟不足以验证对战。渲染插值使用服务器帧时间，避免将到包抖动映射成车速抖动。
- 先验证宿主是否会导出/复制 match state。Nakama 3.40 的普通返回 state 不能容纳循环引用物理世界；每局独立 VM 的闭包方案依赖已确认的宿主生命周期，不能套用于共享 RPC 池。
- 回放和影子使用一个记录格式；完整记录复现全部车辆，影子投影一辆车且没有碰撞体。最近 N 条与最快记录的淘汰策略分开，赛道/版本/发车位不兼容时不可混比。


## 2026-09-08 补充：显示相位、全局排序与文本宿主

Tamaweb案例：保留一帧中draw、onLateDraw、相机回调的真实次序。记录可见状态与下一模拟状态，最终刷新截图不能无意中再前进一帧。固定相位必须声明步长、尾段及delta上限；原函数边界stub要明确排除的玩法/音效/粒子，不能把移植实现生成的预期当独立源证据。

场景父子关系可能只控制坐标与生命周期，源渲染仍全局按z/depth/localZ排序。目标树形渲染若按整组输出，跨组相邻物体会遮挡错误。按源全局顺序制作Prefab，并在运行时只更新已保存图层的属性。Math.round须在相机和所有父坐标累加后发生。Cocos工具响应成功后仍需重开检查真实层序/自定义脚本CID。

CSS字体关键字、normal行盒和Canvas.font解析不必相同；分别记录实际宿主测量。排版可以在字体加载后读取不可见测量结果，但可见界面应继续由目标平台原生组件承担，测量用临时对象须清除。

## 2026-09-27 重组补充：粒子独立轨迹

复制组件后先验证世界坐标，避免缺少父节点偏移。用高空副本隔离碰撞并按seed对应连续帧，分别反推发射面、速度法线、重力/阻尼顺序与内部子步。粒子空间和形状枚举必须核对原生getter及目标引擎枚举，不能直接拷贝整数。临时副本须在主线程finally销毁，副本结果不代替完整实战碰撞证据。

## 2026-09-28：先核对实际渲染路径，再修视觉

字体图集像素格不一定等于实际网格尺寸。若项目已有自定义字形renderer，应采样其使用的runtimeGlyphs和原网格，再判断是否需要放大。局内计分与结算取整要分别核对，避免HUD提前丢失小数；权益改变时长时，进度条分母应使用该局最大时长。只读实战采样与纯格式调用要区分，普通矿样本不能声称覆盖富矿。

## 2026-09-28：手动发射的首帧与变帧率验证

emit与update分离时，出生属性不一定已适合直接提交。检查真实引擎的reset/init/animate顺序，只在新生粒子上以dt=0补初始化，不推进整个粒子系统。原版轨迹需至少区分30/60/120Hz，验证衰减与内部子步；自由运动证据不能证明碰撞一致。独立克隆同一主线程回调清理，保留原游戏状态。见矿山碎石轨迹复盘。

## 2026-09-28：碰撞采样不能用同一数据拟合后自证

先从一组原生数据识别候选接触规则，再用不同帧率和不同朝向的独立样本检验；记录扫掠末端也必须包含余量，否则仅位置公式正确仍会漏碰撞。把由观测速度反推出随机系数的验证明确标为条件验证，避免宣称原随机流已复现。浏览器无错误只能证明可运行，截图发现的遮挡/地面问题仍需保留待办。

## 2026-09-28：候选排序也是随机布局的输入

重组补充：噪声常量必须还原源单精度；对候选降序后按索引抽样的逻辑，同分值的排序交换顺序决定后续随机标记位置，不能默认稳定排序等价。用原函数在隔离数据上运行，捕获完整候选顺序、随机种子和最终标记；若需触碰全局随机流，在同一主线程回调finally恢复并验证。独立测量进场成本，避免把它当作FPS收益。案例见[矿山布局排序](../90-项目案例归档/2026-09-28-idlecat-矿山布局排序-阶段复盘.md)。
